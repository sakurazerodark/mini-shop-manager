# 需求补充与实施规划

本文档记录店小易现阶段新增的业务需求，作为后续设计、开发和验收的共同依据。文中的“必须”表示验收条件；尚未确定的参数集中在“待确认事项”。

## 1. 账号与权限管理

### 1.1 目标

引入账号、角色和权限模型，控制配置、收银、退款、报表和数据维护等操作。支付配置和退款属于高风险操作，必须有独立权限，不能只依赖页面是否显示按钮。

### 1.2 初始角色建议

| 角色 | 适用人员 | 默认能力 |
| --- | --- | --- |
| 店主/超级管理员 | 门店负责人 | 全部功能、账号和角色管理 |
| 管理员 | 店长 | 日常业务、报表、支付方式维护；不能管理超级管理员 |
| 收银员 | 前台收银人员 | 收银、查看本人或当日订单；不能修改支付配置 |
| 财务/审计 | 对账人员 | 查看订单、支付记录、退款记录和报表；退款需单独授权 |
| 只读用户 | 查看人员 | 只读访问已授权的页面和报表 |

角色只是默认模板，实际访问以权限点为准。

### 1.3 权限点要求

权限采用 `资源.动作` 命名，并预留数据范围（全部门店、指定门店、本人创建、指定时间范围）字段。首批至少包含：

- 账号与角色：`account.view`、`account.manage`、`role.view`、`role.manage`。
- 支付设置：`payment.config.view`、`payment.config.manage`、`payment.method.manage`。
- 收银与支付：`payment.create`、`payment.confirm`、`payment.record.view`、`payment.reconcile`。
- 退款：`refund.view`、`refund.request`、`refund.approve`、`refund.execute`。是否需要审批由门店策略决定，但执行权限必须独立存在。
- 报表与订单：`order.view`、`order.manage`、`report.view`、`report.export`、`exception.manage`。
- 数据归档：`archive.view`、`archive.run`、`archive.restore`。

### 1.4 行为与审计

- API 和桌面端都必须校验权限；未授权请求返回明确的无权限错误，不得仅依赖前端隐藏按钮。
- 支付配置中的密钥、证书和私钥只允许有权限的用户查看或修改，日志中不得记录明文。
- 修改支付配置、调整支付方式排序、发起或执行退款、手动处理异常订单、运行或恢复归档都要记录操作人、时间、对象、变更摘要和结果。
- 为未来的精细化权限保留权限版本、角色继承或组合、资源范围和临时授权字段；新增权限不应破坏已有角色配置。

### 1.5 验收标准

1. 不同角色登录后只能看到并调用已授权的菜单和接口。
2. 无 `payment.config.manage` 的账号不能保存支付设置，无 `refund.execute` 的账号不能确认退款。
3. 所有高风险操作都能在审计记录中追溯到账号和结果。
4. 权限拒绝、会话失效和账号禁用都有一致的错误提示和处理。

## 2. 支付设置与支付方式

### 2.1 支付方式模型

支付方式需要同时保存“收款场景分类”“线上支付渠道（如有）”“显示名称”“启用状态”“排序值”“默认标记”和必要的配置引用。线上支付渠道限定为支付宝、微信支付、云闪付，不能把渠道名称直接当作收款场景。

按实际列出的业务场景，支付方式固定拆为以下五类：

1. 客户扫动态码：门店为当前订单生成动态码，客户扫码付款；必须可选择并记录支付宝、微信支付或云闪付渠道。
2. 商家扫客户码：收银员使用扫码枪或摄像头扫描客户付款码；必须可选择并记录支付宝、微信支付或云闪付渠道。
3. 商家上传静态二维码供客户扫：门店绑定并展示自有静态收款码。
4. 现金支付。
5. 其他方式：例如银行卡、挂账或人工收款，需支持自定义名称和备注。

### 2.2 设置能力

- 支付配置页面的子页面顺序固定为“通用配置、支付宝、微信支付、云闪付”，打开支付配置时默认进入“通用配置”。
- 支持启用/停用支付方式，设置唯一默认支付方式，并在默认方式被停用时要求重新选择或明确回退规则。
- 支持拖拽或上移/下移自定义支付方式顺序；顺序必须持久化，并在收银台、退款方式选择和报表筛选中保持一致。
- 支持按收款场景配置线上渠道和渠道参数。支付宝、微信支付、云闪付的密钥配置分别保存，互不覆盖。
- “客户扫动态码”和“商家扫客户码”是收款场景，不是支付宝专属方式；配置页必须为两个场景分别选择线上渠道，收银台根据场景绑定的渠道动态选择下单、扫码和支付状态查询实现。
- 当所选渠道未完成配置或暂未接入时，该场景显示渠道状态并禁止收款，不能静默回退为其他渠道。
- 静态二维码支持上传、替换、预览、删除和格式/大小校验；配置变更需要记录审计日志。
- 支持组合支付时按实际拆分金额记录每个支付方式，退款和报表不得丢失拆分明细。

### 2.3 扫码输入隔离

修复“商家扫客户码被当作商品输入”问题：

- 收银台进入“商家扫客户码”收款状态后，扫码输入只进入支付码解析器，不得调用商品条码查询或加入购物车。
- 支付状态结束、取消或超时后，扫描器恢复商品录入模式；模式切换要有明确的状态提示和可取消操作。
- 支付码解析失败时显示支付码错误，不得静默降级为商品条码；只有用户明确退出支付扫码状态后才允许重新录入商品。
- 键盘扫码枪、摄像头扫码和手动输入应使用同一套状态机和校验规则，并记录支付码来源。

### 2.4 验收标准

1. 默认支付方式和自定义排序在重启后保持不变，收银台展示顺序正确。
2. 每种方式都能明确显示其收款场景、线上渠道和配置状态；未配置的线上渠道不能被误认为可用。
3. 在商家扫客户码状态下扫描付款码不会新增商品；退出该状态后商品扫码仍正常工作。
4. 支付配置和退款操作分别受权限控制，并产生审计记录。

## 3. 明细和报表

### 3.1 分页规则

- 订单明细、支付记录、异常明细等传统列表使用服务端分页，接口统一接收 `page` 和 `pageSize`，返回 `items`、`page`、`pageSize`、`total` 和 `totalPages`。
- 页面提供 pageSize 选择和页码导航，切换筛选条件或排序时回到第 1 页；翻页过程中保留筛选条件。
- pageSize 提供有限的可选值（建议 20、50、100），服务端限制最大值，避免一次查询加载全部历史数据。
- 瀑布流或连续加载页面不强制增加传统页码，但必须有明确的加载中、没有更多和失败重试状态。

### 3.2 时间范围筛选

订单明细、支付记录、异常明细都增加开始时间和结束时间筛选，默认范围为当前本地日期 `00:00:00` 至 `23:59:59.999`。日期计算和数据库查询必须使用统一的门店时区，避免跨日数据错位。

筛选器至少提供“今天、昨天、近 7 天、自定义”快捷选项；清空筛选时恢复默认的当天范围。日期范围要传递到服务端，不能只在前端对已加载数据过滤。

### 3.3 验收标准

1. 三类明细首次打开只查询当天数据，并显示当前页、总条数和 pageSize。
2. 调整 pageSize、翻页、切换标签页后不会丢失时间范围和其他筛选条件。
3. 服务端返回的总数与导航页数一致，最后一页数据量正确。
4. 跨午夜和夏令时（如运行环境支持）查询结果按门店时区计算；无结果时展示空状态而不是报错。

## 4. 历史冷数据归档

### 4.1 目标与范围

对订单、订单明细、支付记录、退款记录、异常记录及相关审计日志进行定期归档，降低在线数据库体积和查询压力。库存当前状态、商品主数据和未完成订单不得被归档。

### 4.2 归档策略

- 归档周期和冷数据阈值可配置，建议默认归档超过 24 个月且已完成、已退款或已关闭的记录。
- 提供定时任务（建议按月执行）和管理员手动触发两种方式；任务需支持预览待归档数量、断点续跑和失败重试。
- 归档前执行一致性校验和备份，归档过程采用事务或可恢复批次，避免只迁移主表而留下孤儿明细。
- 归档数据写入独立的归档库或按周期生成只读文件，保存归档批次、时间范围、记录数、校验值、执行人和结果。
- 在线报表默认查询热数据；用户拥有 `archive.view` 时可按时间范围检索归档数据，结果应标记为“归档数据”。恢复操作需要 `archive.restore`，并记录审计日志。
- 在删除在线数据前提供校验、导出和保留期策略，归档文件应纳入现有数据库备份流程。

### 4.3 验收标准

1. 定时任务按配置周期运行，重复执行不会重复归档同一批记录。
2. 归档后订单、支付、退款和异常记录的关联关系、金额和时间保持一致。
3. 在线查询不受归档任务长时间锁表影响；任务失败可查看原因并重试。
4. 有权限的用户可以查询归档记录，无权限用户无法读取或恢复归档文件。

## 5. 实施顺序与待确认事项

建议按以下顺序实施：

1. 账号、角色和权限基础设施，优先落地支付配置和退款权限。
2. 支付方式数据模型、默认值/排序、扫码状态机和支付配置界面。
3. 报表统一查询参数、服务端分页和当天默认时间范围。
4. 归档任务、归档存储、历史查询和恢复流程。

开发前需要产品确认：

- 退款是否启用“申请-审批-执行”两人流程，还是由单一 `refund.execute` 权限直接完成。
- 冷数据默认保留多少个月，以及归档文件保存位置、加密和备份保留期。
- “其他方式”是否允许门店新增自定义支付方式，以及是否需要组合支付的拆分退款规则。
